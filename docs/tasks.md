## Risks / follow-ups

- Probe classification uses raw-line substring heuristics for tool/model-turn
  boundaries because provider event shapes drift. Evidence transcripts are kept
  so a mis-heuristic can be re-derived without re-running.
- `resume_after_clean_exit` is treated as sufficient proof of
  `session_survives_process_exit`; a dedicated on-disk session-file check can be
  added if a provider ever resumes from memory.
- Codex probe uses the CLI default model unless `MM_CODEX_MODEL` is set, to avoid
  invalid-model failures; the model used is recorded in the matrix.
- Live probes cost real (small) model turns and take a few minutes.

### M0 drift review (2026-08-29)

What was proven (live, versions Claude Code 2.1.251 / Codex CLI 0.150.1; full
matrix in [`provider-capabilities.md`](provider-capabilities.md), raw evidence
under gitignored `.mm/probes/`):

- Both CLIs emit a durable session/thread id and token usage in their structured
  stream, and both resume by explicit id after: clean exit, SIGINT during an
  active turn, SIGINT during a real long tool command (`sleep 20`, observed
  `in_progress`), an uncatchable SIGKILL of the process group, from a linked git
  worktree, and when the same id is resumed twice.
- No orphaned `sleep` child survived the process-group SIGINT for either
  provider, and the worktree stayed clean.
- Claude print mode accepts a follow-up message into the same running process via
  `--input-format stream-json` (`mid_process_steer` yes). Codex `exec` is
  single-shot (stdin is `/dev/null`) and its resume always requires a prompt
  (`requires_resume_prompt` yes) — there is no promptless follow mode.

What changed versus assumptions: the pessimistic hypotheses did not materialize.
The public Claude print-mode "cannot resume" reports concern the interactive
`--resume` picker; resume by explicit session id worked in every scenario,
including from a git worktree. So the plan's optimistic branch holds: for these
two versions, M3 adapters MAY offer interrupt steering rather than being limited
to checkpoint-plus-recovery.

Important nuance (kept honest in the matrix): `resume_after_sigint_model_turn` is
the weakest proof. Claude was interrupted at the tail of the turn (base exit 0,
~3.7s) and Codex at `turn.started` (base exit 1, ~0.5s). Mid-generation interrupt
timing is inherently racy and per-provider. The strong, unambiguous guarantees
are `resume_after_sigint_tool` (interrupts a real in-progress command) and
`resume_after_sigkill` (crash recovery). Recovery must still never infer success
from a missing process — that goal is unchanged and remains enforced by design,
not by these probe outcomes.

Is any goal or plan sentence now wrong? No. The product intent was unchanged, and
the fail-closed policy still held ("until a provider/version passes those tests,
expose only checkpoint-at-completion steering"); we now have a passing record for
these two versions, and the delivery phases are annotated with M0. The adapter
capability record must be re-probed on any CLI version change (both drift often).
(The former `docs/goals.md` and `docs/technical-plan.md`, referenced by earlier
entries, have since been removed.)

`mm repo add`, README; no live workers). Blocked on human approval per the

## M4 — autonomous completion (2026-08-29)

The manager can now close the loop without a human in the routine path: resolve a
worker's question from a durable decision, review the exact work, and deliver a
PR — with a hard gate that refuses to ship anything not reviewed at its current
head.

What changed and why:

- **Durable scoped decisions** ([`src/middle_manager/decisions.py`](../src/middle_manager/decisions.py)).
  A decision records the normalized-question fingerprint, answer, scope
  (`task` | `run` | `global`), provenance, and can be superseded without erasing
  history. `find_matching` resolves by precedence (global > run > task, most
  specific/recent wins). This is goal 6 ("preserve decisions without making them
  timeless").
- **Autonomous question routing**
  ([`supervisor/core.py`](../src/middle_manager/supervisor/core.py)). When a
  worker blocks on a question, the supervisor consults decisions and, on a match,
  emits `auto_answered` and resumes the worker itself — no human. A question that
  reappears *after* its stored answer was applied is escalated as `blocked`
  (actionable) instead of looping. `mm answer <task> --answer ... [--scope]`
  records the user's answer as a decision and resumes; the same answer is then
  reused for equivalent questions in scope.
- **Exact-HEAD review gate** ([`src/middle_manager/review.py`](../src/middle_manager/review.py)).
  A review is bound to the precise commit SHA it examined. `is_approved_at_head`
  returns false if the latest verdict is not `approved` or if the worktree moved
  past the reviewed SHA. `mm review show|approve|request-changes|status`.
- **Gated delivery** ([`src/middle_manager/delivery.py`](../src/middle_manager/delivery.py)).
  `mm deliver <task>` refuses unless approved-at-head, then pushes the lease
  branch (plain git, any origin) and opens a PR via `gh-axi`/`gh` when present.
  This is the only outbound path and the most conservative step (goal 5, delivery
  gates enforced in code, and goal, "approvals match exact head commits").
- **Lavish feedback loop** ([`src/middle_manager/artifacts.py`](../src/middle_manager/artifacts.py)).
  `mm artifact <run> --title --sections` writes a self-contained HTML review
  surface plus a JSON feedback sidecar; `mm feedback <id>` reads structured
  feedback back and flips the artifact to `closed` when the user closes the
  session. Fully local and dependency-free; `lavish-axi` is preferred when
  installed (goal 9).
- **Cross-repo rollout order** ([`src/middle_manager/crossrepo.py`](../src/middle_manager/crossrepo.py)).
  `mm plan <run>` topologically orders tasks over their dependency edges and
  refuses on cycles or dangling (out-of-run) edges, so shared-contract changes
  ship in a safe sequence (goal 4).
- **Lifecycle hooks** ([`src/middle_manager/hooks.py`](../src/middle_manager/hooks.py)).
  `mm hook <event>` reads a JSON payload on stdin and records a durable
  `hook_<event>` lifecycle event against the task/run — the supervision seam for
  interactive managers. Tolerates non-JSON input.

Example commands:

```
mm dispatch --repo demo --title "needs input" --provider fake --instructions "ASK:which port?"
mm answer 2 --answer "8080" --scope run          # records a decision + resumes
mm review show 1                                  # base..head diffstat
mm review approve 1 --findings lgtm               # binds approval to the head SHA
mm deliver 1 --no-pr                              # refused unless approved-at-head
mm artifact 1 --title "Design review" --sections '[{"heading":"Naming","body":"...","options":["keep","rename"]}]'
mm feedback 1
mm plan 1
```

Verified by 74 hermetic tests (decisions precedence/supersede, the review gate
reopening when head moves, delivery refusal + real push after approval, cross-repo
ordering/cycles/missing edges, the artifact roundtrip, hook ingestion, and an
end-to-end autonomous auto-answer through the supervisor + fake worker), plus a
live CLI smoke: `dispatch → review show → deliver (refused) → approve → deliver
(pushed) → plan`, the `answer` auto-resume path, and rendering the Lavish HTML
artifact in a browser. Lint/format clean.

## M5 — hardening (2026-08-29)

The final milestone makes the system safe to leave running: durable state
survives restarts, half-alive runners are reconciled fail-closed, decisions can
go stale and be managed, usage is auditable, and `mm doctor` surfaces the two
things that silently rot (capability-matrix drift and schema version).

What changed and why:

- **Restart / replay / reconcile recovery**
  ([`tests/test_recovery.py`](../tests/test_recovery.py)). Proven: a fresh
  supervisor over the same `.mm` reconstructs a completed run and its actionable
  events from SQLite; the append-only spool mirrors the streamed worker events
  one-to-one and each spool line is a valid record (replayable); a runner whose
  process vanished without a result is marked `orphaned` and its task
  `needs_recovery` with an `error` event — never assumed successful (goal 7).
- **Decision staleness + memory controls**
  ([`decisions.py`](../src/middle_manager/decisions.py),
  [`state/db.py`](../src/middle_manager/state/db.py) schema v3). Decisions now
  carry an optional premise `context` and an `invalidated_at`. On reuse,
  `find_matching(context=...)` raises `StaleDecision` when the winning decision
  was recorded under a different non-null premise, so the manager asks only for
  the delta instead of silently reusing a timeless preference (goal 6). The
  supervisor computes a task's context from its repo base SHA and escalates a
  stale premise as `blocked`. `mm decision list [--all] | invalidate | forget`
  lets the user inspect, invalidate (history preserved), or hard-delete (goal 8).
  A forward-only migration adds the columns to pre-existing databases.
- **Usage reports** ([`state/store.py`](../src/middle_manager/state/store.py),
  `mm usage <run>`). Per provider/model/reasoning token totals and call counts,
  plus a run total — the auditable "how much usage was incurred" the goals ask
  for.
- **`mm doctor` polish** ([`setup/doctor.py`](../src/middle_manager/setup/doctor.py)).
  Compares each provider's recorded probe version against the installed CLI and
  flags drift ("re-probe before trusting steering"), and reports the state-DB
  schema version against the expected one.

Example commands:

```
mm doctor                          # now includes capability drift + schema version
mm usage 1                         # tokens by provider/model, plus a total
mm decision list --all             # includes superseded/invalidated
mm decision invalidate 3           # stop reusing a decision (history kept)
mm reconcile                       # mark vanished runners needs_recovery
```

Verified by 83 hermetic tests (recovery/replay/reconcile, decision
staleness/invalidate/forget/list, usage aggregation, doctor drift+schema, semver
drift extraction) plus a live CLI smoke: `doctor` drift/schema output, the
`answer → decision list → invalidate` memory loop, and `usage`. Lint/format clean.

## Proactive performance self-assessments (2026-08-29)

User: *"The middle manager should periodically perform self assessments, identify
opportunities to improve their performance, set an action plan, and align with the
user on how they will be better in the future than they were in the past. The user
should not need to initiate this."* This is an explicitly approved cross-cutting
addition to M4/M5, not a relaxation of the authority model or a claim that either
milestone is otherwise complete.

The implementation and runtime contract follow these decisions:

- **Evidence is collected automatically.** The control plane builds a deterministic
  packet from durable run/task outcomes, reviews and rework, retries/recovery, cycle
  time and usage, escalations and repeated questions, decision reuse, user
  corrections, cross-repo coordination, and progress against the previous plan. The
  manager assesses evidence; it does not grade itself from vibes.
- **Formal cadence is bounded.** A review becomes due after **five completed runs or
  14 days**, whichever comes first, but only with enough completed work to support a
  conclusion and with at least a **seven-day cooldown** between formal reviews.
  Significant failure, repeated rework, or repeated user correction can surface an
  earlier evidence-based review without turning every noisy run into a crisis
  meeting. The defaults are policy, not prompt lore, and remain editable later through
  `mm config assessments`.
- **The manager initiates it.** Supervisor and Claude/Codex lifecycle-hook delivery
  surface due reviews into the active manager session; durable state carries the
  obligation across interruption or restart. The user does not run a retrospective
  command or remember the schedule.
- **The output is an experiment plan, not a promise.** Each review records what
  improved, what underperformed, and **one to three** proposed experiments with an
  observation, likely cause, concrete behavior change, baseline, target, and future
  evidence. Mechanics are exposed as `mm assessment tick|status|show|complete|align`
  so delivery is deterministic and recoverable across both harnesses.
- **User alignment is durable and context-sensitive.** The manager brings the
  evidence and proposed plan to the user, then records approval, revision, or
  dismissal in authoritative SQLite state and curates the active plan in
  `.mm/memory/improvements.md`. It reuses that decision while the premises hold and
  does not relitigate it. Materially changed evidence, constraints, scope, or
  direction justify asking again — with the delta made explicit.
- **The walls do not move themselves.** Routing, sequencing, memory use, caching, and
  other reversible operating practices may improve inside existing authority.
  Changes to model/reasoning/spend ceilings, config, standing authority, framework
  source, hooks, skills, or safety gates remain proposals until the user approves
  them.

Documentation is aligned in the runtime contract, the `self-improvement` and
`durable-memory` skills, README, and the implementation plan.

Implementation: schema v4 adds durable assessment/action records;
[`assessments.py`](../src/middle_manager/assessments.py) owns evidence, cadence,
transitions, measurable-action validation, and memory projection; supervisor/task
completion prepares due work; checked-in Claude/Codex SessionStart + Stop hooks deliver
it without a recursion loop; and `mm config assessments` keeps cadence editable.
Validation: `make fmt`, `make lint`, and the full hermetic suite pass (**135 green**, 5
live tests deselected).

## Session handoff and worker health (cross-cutting, 2026-08-29)

What and why: the manager's working context — what the user asked for, what was
decided, what's next, what's waiting on whom — was the one thing that did not survive
a compaction, a closed terminal, or a new day. Worker lifecycle is durable in SQLite
and memory is durable Markdown, but nothing produced a resumable view of *this
session*, and nothing noticed a worker that had simply gone silent. Two principles:
**record state first, then hand off** (the board and memory are the record; the
handoff stores nothing of its own), and **team health is polled by code, not
remembered by the model**.

- **`handoff` skill** ([`.agents/skills/handoff/SKILL.md`](../.agents/skills/handoff/SKILL.md),
  user-invocable; `.claude/skills/handoff` is a symlink so Claude Code exposes it as
  `/handoff` — Claude Code only scans `.claude/skills/` but follows symlinks; Codex
  reads `.agents/skills/` natively). Procedure: (1) make the work board true — its
  `Backlog / next` section is where intent survives; (2) `mm handoff`; (3) reply with
  the risks in plain words, then the pickup prompt verbatim in a code block. Every
  invocation ends with the prompt. The skill also owns the *resume* side: reconnect
  to the team (`mm supervisor status` → start if down → `mm reconcile` → `mm health`),
  load memory, reconcile the snapshot against live state, then speak.
- **`mm handoff [--json]`** ([`handoff.py`](../src/middle_manager/handoff.py)): reads
  open runs and task states, open questions, review status, the board's
  `In flight` / `Blocked / needs me` / `Backlog / next` bullets (seeded placeholders
  dropped), pings the supervisor (3s timeout; never raises), and runs the health check.
  It prints a self-contained **pickup prompt** with reconnect steps, the snapshot, and a
  **"Known risks at handoff"** block: supervisor down/hung with tasks in flight, dead
  worker processes, quiet workers, workers still running (results and questions queue
  unanswered; a dead terminal takes them down), tasks idle on a question, finished work
  awaiting review, and an untouched board while runs are open. Warnings also go to
  stderr. Nothing is written to disk — an earlier `handoff.md` packet design was dropped
  on the user's direction.
- **Worker health** ([`health.py`](../src/middle_manager/health.py)): per in-flight
  task, `alive` / `quiet` / `dead` from the runner pid and the newest `events` row for
  the task (the runner already records every worker stream event; `runners.heartbeat_at`
  was never updated, so "last heard" is derived from events, falling back to the task
  row). `mm health [--quiet-minutes N] [--json]` prints it (exit 1 when anything is
  not alive). The supervisor's serve loop now runs `_tick_health()` every 60s and raises
  one actionable **`worker_quiet`** event per quiet episode (re-armed when the worker
  speaks again), so `mm run` / `mm wait` surface a stuck worker like any other
  actionable moment. Threshold is `[health] quiet_minutes` (default 15) via
  `mm config health --quiet-minutes N`; `worker_quiet` was added to `ACTIONABLE_KINDS`.
- **Contract/role**: `docs/manager-runtime.md` skills index gains `handoff`; `_ROLE`
  gains HANDOFF and TEAM HEALTH clauses (reply with the prompt verbatim; treat
  `worker_quiet` as actionable — peek, steer, resume, or reconcile).
- **Tests**: [`tests/test_handoff.py`](../tests/test_handoff.py) (board parsing, run
  bucketing, every warning class, self-contained prompt, nothing stored, CLI/JSON) and
  [`tests/test_health.py`](../tests/test_health.py) (verdicts, last-heard fallback,
  once-per-episode flagging + re-arm, the supervisor tick, config threshold + CLI).
  `make fmt`, `make lint`, full hermetic suite: **148 green**, 5 live deselected.

## Code-owned task tracking (cross-cutting, 2026-08-29)

What and why: task tracking was two-sourced — `state.db` (code-owned, always right,
coarse) and the Markdown board / per-repo `tasks.md` (model-owned, richer, unenforced;
on this machine the board was still the seeded template with a run open). Three
changes make intent and progress **structured and code-owned, with Markdown as a
projection**:

1. **Manager intent ledger** — schema **v5** adds `todos` (text, status
   open/done/dropped, `blocked_on`, optional run/task, position).

   (`add|done|drop|reopen|block|unblock|edit`, blocker vocabulary

   `mm todo list [--all] [--run] [--json]`. **`mm board [--write]`** renders the work
   board from the ledger + live task states (with each in-flight task's latest phase),
   and every ledger mutation rewrites `.mm/memory/tasks.md` — the file is now a
   generated projection with a "do not hand-edit" banner; the seeded template says so.
   `mm status` shows in-flight / waiting task counts and next / waiting todo counts.
   `mm handoff` and the **SessionStart hook** read the ledger: `hooks.session_start_context`
   injects a compact pickup context (next steps, waits, open runs with each task's phase,
   and the team-risk warnings) as `additionalContext` — on a fresh session *and* after a
   compaction — alongside any due assessment.
2. **Worker progress as events** — [`progress.py`](../src/middle_manager/progress.py):
   `mm progress <task_id> --phase plan|implement|test|review|blocked|done --note …`
   appends a `worker_progress` event (a plan needs a note). `mm progress <id>`
   / `--history` inspect; `mm task <id>` prints the latest report; `mm memory show
   --repo <name>` now renders the repo's progress log from events before the files.

   repo `bin/` to PATH (a worker's cwd is its worktree, and `mm` resolves `.mm` from

3. **Enforcement where it's cheap** — `hooks.stop_block_reason`: the Stop hook blocks

   takes precedence as before.

Contract, `_ROLE`, and the `durable-memory` / `handoff` / `self-improvement` skills now

## Lease lifecycle on dispatch and worker failure (2026-08-30)

Two runtime failures from a real session: a dispatch whose treehouse lease could not
be acquired left a `requested` task with no runner and printed `dispatch failed:

- `Supervisor.dispatch_task` now catches `LeaseError`: the task row (already created

- `Supervisor._run_task` calls `_release_lease_if_pristine` after every run: a task
  that ended `failed` with a clean worktree at its base SHA has its lease released

  worktree is kept for inspection and `mm resume`.
- Fake worker gains a `DIRTY_FAIL` marker (writes an uncommitted file, then fails).
- Tests: [`test_lease_lifecycle.py`](../tests/test_lease_lifecycle.py) — lease failure
  marks the task failed with the reason and leaves no active lease; pristine failure
  releases; dirty failure keeps.
